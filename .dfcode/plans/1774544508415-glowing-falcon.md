# Allo Docker Appliance Packaging Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Package Allo as a Docker Appliance: one command install, browser access, no manual config file editing.

**Architecture:** Keep existing 4-service stack (nginx/frontend/gateway/langgraph), add bundled Postgres, ship default configs inside images, add first-run web wizard that writes settings to DB and generates runtime config files.

**Tech Stack:** Docker Compose, PostgreSQL, FastAPI, Next.js, SQLAlchemy, Better Auth

## Phase 1: Docker Compose 产品化

目标：客户只需 `docker compose up -d`，无需提前创建任何配置文件。

### Task 1.1: 添加 Postgres 服务

**Files:**
- Modify: `docker/docker-compose.yaml`

在 services 中添加 postgres 容器，使用 named volume 持久化数据：

```yaml
postgres:
  image: postgres:16-alpine
  container_name: deer-flow-postgres
  environment:
    POSTGRES_DB: deerflow
    POSTGRES_USER: deerflow
    POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-deerflow_secret}
  volumes:
    - pgdata:/var/lib/postgresql/data
  networks:
    - deer-flow
  restart: unless-stopped
  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U deerflow"]
    interval: 5s
    timeout: 3s
    retries: 10

volumes:
  pgdata:
  appdata:
```

让 gateway 和 langgraph 都 `depends_on: postgres: condition: service_healthy`。

将 gateway/langgraph 的 `DATABASE_URL` 统一设为：
`postgresql+asyncpg://deerflow:${POSTGRES_PASSWORD:-deerflow_secret}@postgres:5432/deerflow`

### Task 1.2: 内置默认配置，去掉宿主文件挂载依赖

**Files:**
- Modify: `docker/docker-compose.yaml`
- Modify: `backend/Dockerfile`
- Modify: `backend/langgraph.json`

当前问题：gateway 和 langgraph 都通过 volume mount 从宿主机读 `config.yaml` 和 `extensions_config.json`，要求客户提前准备好这些文件。

改法：
1. 在 `backend/Dockerfile` 中 COPY `config.example.yaml` → `/app/config.yaml` 和空 `extensions_config.json` → `/app/extensions_config.json` 作为镜像内默认值
2. 改 compose 中 gateway/langgraph 的 volume mount 为可选：用 `appdata` named volume 挂载 `/app/data`（运行时数据目录），不再强制挂载宿主 config 文件
3. 修改 `backend/langgraph.json` 的 `"env": ".env"` → 删除此字段或改为空，改用 compose 的 `environment` 和 `env_file` 统一注入环境变量
4. gateway 和 langgraph 的 `DEER_FLOW_CONFIG_PATH` 统一指向 `/app/data/config.yaml`（运行时生成）或 fallback 到镜像内置的 `/app/config.yaml`
5. `DEER_FLOW_HOME` 统一指向 `/app/data/.deer-flow`

### Task 1.3: 创建一键启动脚本

**Files:**
- Create: `install.sh`

一个极简的安装脚本，客户只需：
```bash
curl -fsSL https://your-domain/install.sh | bash
```

脚本做的事：
1. 检查 Docker 和 Docker Compose 是否安装
2. 创建工作目录（如 `~/allo`）
3. 下载 `docker-compose.yaml`（或从镜像中提取）
4. 生成随机 `POSTGRES_PASSWORD` 和 `BETTER_AUTH_SECRET` 写入 `.env`
5. `docker compose up -d`
6. 打印访问地址 `http://localhost:2026`

## Phase 2: 后端 Appliance 配置存储

目标：用 DB 替代手动编辑文件，作为安装级配置的 source of truth。

### Task 2.1: 新增 ApplianceSettings DB 模型

**Files:**
- Modify: `backend/app/gateway/db/models.py`

在现有 SQLAlchemy models 中新增一张表：

```python
class ApplianceSettings(Base):
    __tablename__ = "appliance_settings"

    id = Column(String(36), primary_key=True, default=lambda: str(uuid4()))
    key = Column(String(255), unique=True, nullable=False, index=True)
    value = Column(Text, nullable=False, default="{}")
    updated_at = Column(DateTime, server_default=func.now(), onupdate=func.now())
```

用 key-value 存储以下配置：
- `setup_completed` — bool，标记是否完成首次设置
- `model_providers` — JSON，包含所有已配置的模型提供商及其 API key
- `default_model` — string，默认模型名
- `sandbox_mode` — string，sandbox 策略（local/aio）
- `base_url` — string，产品对外访问地址

这张表在 gateway 启动时通过现有的 `Base.metadata.create_all` 自动创建，无需额外 migration。

### Task 2.2: 新增 Setup API Router

**Files:**
- Create: `backend/app/gateway/routers/setup.py`
- Modify: `backend/app/gateway/app.py`（挂载新 router）

新建 `/api/setup` 路由组，不需要认证（因为首次安装时还没有用户）：

```
GET  /api/setup/status     → { "setup_completed": bool, "step": "..." }
POST /api/setup/admin      → 创建首个管理员账号和默认组织
POST /api/setup/models     → 保存模型提供商配置（provider, api_key, model_name）
POST /api/setup/complete   → 标记安装完成，触发配置生成
```

关键逻辑：
- `GET /api/setup/status` 查询 `ApplianceSettings` 中 `setup_completed` 的值，如果表为空或值为 false 则返回未完成
- `POST /api/setup/models` 接收模型配置，验证 API key 有效性（调一次模型 API 测试），成功后写入 DB
- `POST /api/setup/complete` 调用配置生成服务（Task 2.3），将 DB 中的设置渲染为运行时文件

安全约束：所有 `/api/setup/*` 端点在 `setup_completed=true` 后返回 403，防止重复执行。

### Task 2.3: 配置生成服务 — 从 DB 渲染运行时文件

**Files:**
- Create: `backend/app/gateway/services/config_renderer.py`

核心功能：读取 `ApplianceSettings` 中的模型配置，渲染出现有 loader 能直接消费的文件：

1. 生成 `/app/data/config.yaml`：
   - 以 `config.example.yaml` 为模板
   - 只启用用户在向导中配置的模型（去掉 `$ENV_VAR` 占位符，直接写入实际值或通过 env 注入）
   - sandbox 部分根据用户选择设置 `use` 字段
   - 其他字段保持默认值

2. 生成 `/app/data/.env`：
   - 写入模型 API key（`OPENAI_API_KEY=xxx` 等）
   - 写入工具 API key（如果用户配置了的话）

3. 生成 `/app/data/extensions_config.json`：
   - 初始为空 `{"mcpServers":{}, "skills":{}}`
   - 后续通过现有 MCP/Skills 管理 API 修改

生成后，通知 gateway 重新加载配置（调用 `app_config.py` 的 `reload()` 或重启 config 缓存）。

LangGraph 服务需要重启才能读到新配置 — 在 `POST /api/setup/complete` 中可以通过 Docker API 或简单的进程信号触发，或者要求用户在向导完成后手动刷新（首版可接受）。

## Phase 3: 首次运行设置向导

目标：客户打开浏览器后看到引导页面，填完即可使用。

### Task 3.1: 安装状态检测与重定向

**Files:**
- Modify: `frontend/src/middleware.ts`
- Create: `frontend/src/core/setup/api.ts`

改造前端 middleware：
1. 对所有 `/workspace` 和 `/admin` 路由，先调 `GET /api/setup/status`
2. 如果 `setup_completed === false`，重定向到 `/setup`
3. 如果已完成，走正常的 session cookie 检查逻辑
4. `/setup` 路由本身不需要认证

为避免每次请求都调 API，可以：
- 首次检查后在 cookie 中缓存 `setup_done=1`
- 或在 Next.js server component 中做一次检查并缓存

新建 `frontend/src/core/setup/api.ts`：
```typescript
export async function getSetupStatus() {
  const res = await fetch("/api/setup/status");
  return res.json(); // { setup_completed: boolean, step: string }
}

export async function submitModelConfig(config: ModelProviderConfig) {
  return fetch("/api/setup/models", { method: "POST", body: JSON.stringify(config) });
}

export async function createAdminAccount(data: AdminAccountData) {
  return fetch("/api/setup/admin", { method: "POST", body: JSON.stringify(data) });
}

export async function completeSetup() {
  return fetch("/api/setup/complete", { method: "POST" });
}
```

### Task 3.2: 重构设置向导步骤

**Files:**
- Modify: `frontend/src/components/workspace/setup-wizard/setup-wizard.tsx`
- Modify: `frontend/src/components/workspace/setup-wizard/model-selection-step.tsx`
- Rewrite: `frontend/src/components/workspace/setup-wizard/tool-selection-step.tsx` → `admin-account-step.tsx`
- Rewrite: `frontend/src/components/workspace/setup-wizard/agent-setup-step.tsx` → `system-check-step.tsx`
- Modify: `frontend/src/components/workspace/setup-wizard/completion-step.tsx`
- Move: setup page from `/workspace/setup` to `/setup`（新建 `frontend/src/app/setup/page.tsx`）

新的向导步骤：

**Step 1: 系统检查**（替换原 agent-setup-step）
- 调 `GET /api/setup/status` 和 `GET /health` 确认后端可达
- 显示服务状态：gateway ✓、langgraph ✓、postgres ✓
- 自动通过后进入下一步

**Step 2: 创建管理员**（替换原 tool-selection-step）
- 表单：邮箱、密码、确认密码
- 调 `POST /api/setup/admin` 创建首个用户和默认组织
- 创建成功后自动登录（设置 session cookie）

**Step 3: 模型配置**（复用现有 model-selection-step，但改为写入 setup API）
- 选择模型提供商（OpenAI / Anthropic / DeepSeek / Google 等）
- 输入 API Key
- 点击"测试连接"验证 key 有效
- 选择默认模型
- 调 `POST /api/setup/models` 保存

**Step 4: 完成**（改造现有 completion-step）
- 调 `POST /api/setup/complete` 触发配置生成
- 显示配置摘要：已配置的模型、管理员账号
- "进入工作台"按钮跳转到 `/workspace`

修改 `setup-wizard.tsx` 中的 STEPS 定义：
```typescript
const STEPS = [
  { id: "check", label: "System Check", icon: ActivityIcon },
  { id: "admin", label: "Admin Account", icon: UserPlusIcon },
  { id: "models", label: "Models", icon: CpuIcon },
  { id: "done", label: "Done", icon: CheckCircle2Icon },
] as const;
```

## Phase 4: 认证系统产品化

目标：让 appliance 模式有真正可用的登录系统，而不是 dev JSON 文件。

### Task 4.1: 区分 appliance 模式与 dev 模式

**Files:**
- Modify: `frontend/src/app/api/auth/[...all]/route.ts`
- Modify: `frontend/src/server/better-auth/local-dev.ts`
- Modify: `backend/app/gateway/auth.py`

当前状态：前端 auth 完全基于 JSON 文件（`data/local-dev-auth-*.json`），后端有 3 层 fallback（DB session → dev session → dev JSON）。

改法：
1. 新增环境变量 `ALLO_MODE=appliance|development`，compose 中默认设为 `appliance`
2. 前端 auth route：
   - `appliance` 模式：使用真正的 Better Auth 库连接 Postgres（需要安装 `better-auth` 的 Postgres adapter）
   - `development` 模式：保持现有 JSON 文件行为
3. 后端 `auth.py`：
   - `appliance` 模式：只走 DB session 验证，禁用所有 dev fallback
   - `development` 模式：保持现有行为
4. Setup wizard 的 `POST /api/setup/admin` 需要直接操作 Better Auth 的 `user`/`account` 表创建首个用户

### Task 4.2: Better Auth Postgres 集成

**Files:**
- Modify: `frontend/src/server/better-auth/server.ts`
- Possibly modify: `frontend/package.json`（添加 better-auth postgres adapter 依赖）

当前 `server.ts` 只有 3 行，基本是空壳。需要：
1. 在 appliance 模式下初始化真正的 Better Auth server，连接 Postgres
2. Better Auth 会自动创建 `user`、`session`、`account`、`verification` 表
3. 配置 `BETTER_AUTH_SECRET`（已由 install.sh 自动生成）
4. 配置 `BETTER_AUTH_URL` 为产品访问地址

目标：MCP、Sandbox、IM 等高级功能在容器中正常工作。

### Task 5.1: MCP 配置通过 UI 管理

**Files:**
- 无需新增文件，复用现有：
  - `backend/app/gateway/routers/mcp.py`（已有 `GET/PUT /api/mcp/config`）
  - `frontend/src/components/workspace/settings/tool-settings-page.tsx`（已有 MCP 开关 UI）

当前 MCP 配置已经可以通过 API 和 UI 管理，`PUT /api/mcp/config` 会写入 `extensions_config.json`。

需要确保：
1. 生成的 `extensions_config.json` 路径在 `/app/data/extensions_config.json`
2. `DEER_FLOW_EXTENSIONS_CONFIG_PATH` 指向该路径
3. MCP 的 HTTP/SSE 类型服务器在容器网络中可达（可能需要 `extra_hosts` 或网络配置）
4. stdio 类型 MCP 服务器需要对应的二进制在容器镜像中（首版可以只支持 HTTP 类型，stdio 标记为"需要自定义镜像"）

### Task 5.2: Sandbox 管理员控制

**Files:**
- Modify: `config.example.yaml` 中 sandbox 部分

首版策略：
1. 镜像内置的默认 `config.yaml` 使用 `local` sandbox（最安全，无需 Docker socket）
2. 如果客户想用容器沙箱，需要在 compose 中手动添加 Docker socket 挂载并修改 sandbox 配置
3. 后续版本可以在 admin UI 中添加 sandbox 模式切换

### Task 5.3: Skills 和 IM 渠道

**Files:**

- 无需改动 IM 代码，保持现有 config.yaml 中的 channels 配置

Skills：
- 内置 skills 目录 COPY 到镜像中 `/app/skills`
- `DEER_FLOW_HOST_SKILLS_PATH` 在 compose 中正确设置
- 用户通过现有 skills settings UI 管理启用/禁用

IM 渠道：
- 保持现有 `config.yaml` 中 channels 配置方式
- 首版客户如需 IM 集成，通过 admin 页面或直接编辑持久化的 config.yaml 配置
- 后续版本可以在 admin UI 中添加渠道配置表单

## Phase 6: 端到端集成与打磨

### Task 6.1: 统一 compose 环境变量

**Files:**
- Modify: `docker/docker-compose.yaml`
- Create: `docker/.env.template`（compose 默认读取的 `.env` 模板）

最终 compose 中只需要这些外部变量（全部有默认值）：
```
PORT=2026
POSTGRES_PASSWORD=deerflow_secret
BETTER_AUTH_SECRET=<auto-generated>
```

所有其他变量（`DATABASE_URL`、`DEER_FLOW_*` 路径、`LANGCHAIN_TRACING_V2` 等）在 compose 内部通过 `environment` 硬编码或从上面三个变量派生。

### Task 6.2: 健康检查与启动顺序

**Files:**
- Modify: `docker/docker-compose.yaml`

启动依赖链：
```
postgres (healthcheck: pg_isready)
  → gateway (depends_on postgres, healthcheck: /health)
  → langgraph (depends_on postgres)
  → frontend
  → nginx (depends_on all)
```

Gateway 的 `/health` 端点增强：检查 DB 连接和 `setup_completed` 状态，返回更丰富的状态信息。

### Task 6.3: 数据持久化验证

确保以下数据在 `docker compose down && docker compose up` 后存活：
- Postgres 数据（用户、组织、appliance settings、tenant config、knowledge base）→ `pgdata` volume
- 运行时数据（.deer-flow、生成的 config 文件、uploads、memory）→ `appdata` volume
- LangGraph checkpoints → 如果用 postgres checkpointer 则在 pgdata 中，如果用 sqlite 则在 appdata 中
