# Async Tool Concurrency Plan

## Goal

Reduce backend blocking caused by `task_tool` while preserving current semantics: the parent agent still waits for the subagent to finish and receives the final result in the same tool call.

## Current Findings

- `langgraph dev` was effectively serializing runs because it defaulted to `N_JOBS_PER_WORKER=1`; that has already been mitigated via startup configuration.
- The next blocking hotspot is `backend/packages/harness/deerflow/tools/builtins/task_tool.py`.
- `task_tool` starts subagent work in the background with `executor.execute_async(...)`, but then blocks the parent tool call by polling in a `while True` loop and sleeping with `time.sleep(5)`.
- Relevant code paths:
  - `backend/packages/harness/deerflow/tools/builtins/task_tool.py`
  - `backend/packages/harness/deerflow/subagents/executor.py`
  - `backend/packages/harness/deerflow/agents/lead_agent/prompt.py`
  - `backend/docs/task_tool_improvements.md`
- We are explicitly not touching shared sandbox file tools (`bash`, `write_file`, `str_replace`, etc.) in this phase, because shared-workspace consistency is a separate design problem.

## Decision

- Scope: first phase only targets `task_tool`.
- Semantics: keep synchronous result semantics from the caller's perspective.
- Risk boundary: do not change shared sandbox/file tool behavior in this phase.
- Runtime config: treat `BG_JOB_ISOLATED_LOOPS` as optional follow-up, not the primary fix for this phase.
- Testing: add the smallest backend test coverage needed for `task_tool` polling/terminal-state behavior, plus manual concurrency verification.

## Recommended Approach

Refactor `task_tool` from sync polling to async waiting while preserving its current UX contract.

Recommended implementation direction:

1. Convert `task_tool` into an async tool implementation so it can await instead of sleeping.
2. Replace `time.sleep(5)` polling with `await asyncio.sleep(...)`.
3. Keep the existing background task model (`execute_async`, background task registry, streaming task events, timeout semantics) intact.
4. Return the same final success/failure/timeout messages so agent prompts and downstream grouping logic do not need semantic changes.
5. Add targeted logging around polling lifecycle if needed to confirm the parent run no longer blocks a worker thread unnecessarily.

Why this approach:

- Smallest safe change with measurable concurrency benefit.
- Avoids changing agent prompting, frontend message expectations, and task result semantics.
- Avoids the harder consistency problem of async/shared file tool execution.
- Aligns with the repo TODO note that specifically calls out replacing `time.sleep(5)` with `asyncio.sleep()`.

## Implementation Steps

1. Inspect `backend/packages/harness/deerflow/tools/builtins/task_tool.py` and identify the minimal changes needed to turn `task_tool` into an `async def` tool while keeping the same arguments and returned strings.
2. Update the polling loop in `backend/packages/harness/deerflow/tools/builtins/task_tool.py`:
   - keep `execute_async(...)`
   - keep status checks and event streaming via `writer(...)`
   - replace blocking sleep with awaited sleep
   - preserve cleanup behavior on terminal states
3. Verify that the existing LangGraph middleware/tool path already supports async tool execution for built-in tools; ensure the change remains compatible with `build_runtime_middlewares()` in `backend/packages/harness/deerflow/agents/middlewares/tool_error_handling_middleware.py`.
4. Review prompt/docs references to `task_tool` behavior:
   - `backend/packages/harness/deerflow/agents/lead_agent/prompt.py`
   - `backend/docs/task_tool_improvements.md`
   Update only if wording is now misleading.
5. Add or adjust backend tests if coverage exists for `task_tool` behavior; if no direct tests exist, add the smallest focused test around non-terminal polling behavior and terminal result handling.
6. Re-run the concurrency reproduction manually after implementation and compare logs for:
   - `run_queue_ms`
   - parent thread responsiveness during `task_tool` execution
   - unchanged final task result behavior

  - Run relevant backend test modules if there is existing coverage around tool execution.

  - Start dev services with current startup script.
  - Trigger a conversation that uses `task_tool`.
  - Confirm the tool still emits `task_started`, `task_running`, `task_completed` / failure events as before.
  - Confirm the final tool return still reaches the parent agent as a normal completed tool result.
- Concurrency check:
  - Reproduce multi-window / multi-thread interaction while one thread is waiting on a subagent task.
  - Inspect `logs/langgraph.log` for reduced queueing and better overlap with other runs.
- Regression check:
  - Ensure no change to shared sandbox tool semantics in this phase.
